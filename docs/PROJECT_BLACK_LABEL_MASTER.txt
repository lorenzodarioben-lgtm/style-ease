# 2. THE DESIGN BRIEF — MUSEUM-GRADE FASHION, NOT A GENERIC STORE TEMPLATE

**Creative territory:** Architectural minimalism, high-fashion editorial direction, editorial print sophistication translated into a tactile digital environment, black / ink / graphite / bone-white / neutral grey. Think gallery, fashion journal, elevated concept boutique and precision product interface. Be visually bold, emotionally arresting, and strategically restrained. Study design principles of high-end fashion editorial sites and premium commerce, but do **not** copy another site's assets, wordmark, layout wholesale, CSS or copyrighted styling.

**Design standard:** Every page must feel like part of an art-directed system. Avoid the familiar small-commerce-template composition with basic blocks, stock grids and badges. Build the layout from typographic rhythm, image composition, negative space, visual hierarchy and deliberate pacing. A premium fashion site has a narrative, not simply sections on a black background.

**Distinctive house identity:** Keep the name **STYLE EASE** and the architectural mood, introduce a clearly visible wordmark/monogram developed in vector/CSS using original geometry. A graphic identity can include recurring line, crop, grid and edition markers, but avoid meaningless decorations. The design must remain recognizable at favicon scale and across mobile/desktop. Define genuine typography hierarchy: display face, body/interface face and optional limited editorial contrast; all appropriately licensed and preferably self-hosted/subset. Avoid default Inter-everywhere blandness; Inter may stay for utility text if paired meaningfully. Documentation must list font licenses.

**Palette:** Near-black core (`#0A0A0A` territory), charcoal layered surfaces, off-white/bone editorial inversions, nuanced grayscale and a single optional subtle warm/metallic editorial accent only when necessary. Design and test text contrast tokens, not just raw hex. Use neutral surfaces rather than decorative colored gradients. Design both dark editorial sections and controlled light-on-dark alternation where it helps narrative clarity. Do not add a generic light/dark mode toggle unless its complete design works equally well.

**Grid and composition:** 12-column or similarly intentional responsive grid on wide screens; purposeful asymmetry and high-impact image crops; varied but systematic section spacing. Use fluid type with `clamp()`, robust container/max-width rules, consistent alignments, meaningful whitespace. Establish layout widths and density modes suitable for catalogue vs editorial story vs checkout. Breakpoints must be based on content, not random conventional numbers.

**Typography:** Oversized, beautiful, legible editorial display; articulate uppercase/letterspacing only where justified; tasteful compact metadata; exact baseline alignment; adequate body line height and button labels. Avoid huge meaningless slogans that push the product below the fold. Contrast should meet WCAG 2.2 AA for applicable text/controls. Do not use display lettering as tiny utility copy.

**Photography/visual asset pipeline:** Treat photographs as first-class product data. Only use real assets with documented permission/source; curate to match the actual listed product, silhouette, cut, material and colour. Prefer a small cohesive collection with strong accurate multi-angle photos to a bigger fake inventory with generic unrelated images. Support AVIF/WebP/responsive fallbacks where tooling supports, `srcset`, `sizes`, object-position, aspect-ratio, blur/dominant-colour placeholders, load-error fallbacks, dimensions, fetch priority and lazy loading. Document remote-image uptime/licensing tradeoffs; avoid critical hero imagery dependent on random third-party URLs. If product media cannot be acquired legally, use clearly designated demo/editorial assets without asserting exact product representation. No unreviewed watermarks or ripped brand photography.

**Motion language:** A quiet choreographed system rather than animation soup: precise hover/focus states, fast drawer movement, card image reveal, controlled page transitions, modest scroll reveals when justified, loading/optimistic feedback. Target roughly 120–280ms utility transitions with calibrated easing; longer hero reveals only if nonblocking. Keep transforms/opacity, respect reduced-motion globally, never delay text/buttons or block initial interaction, avoid scroll-jacking. All animations have functional fallbacks.

**Interaction polish:** Visual changes must be driven by actual state: selection, loading, success, stock exhaustion, empty, error, validation. Buttons and menus must have strong accessible focus. Handle keyboard Escape, outside click, focus return, screen-reader status announcements. Touch hit areas should be large and interactive controls should not depend on hover. The smallest detail — quantity steppers, dropdown focus, selected variants, cart count animation, button disabled states, line separators, responsive footers — must be treated as designed.

**Art direction deliverables:** `docs/DESIGN_SYSTEM.md` covering palette/contrast, typography/fonts/licenses, grids, spacing, corners, borders, motion, image rules, interactive component anatomy and mobile layouts. `docs/ART_DIRECTION.md` with visual rationale, repeated motifs, screenshots and what was deliberately avoided. Provide a real screenshot gallery captured from the running new app, not standalone illustrations.

**Deliberate differentiation:** Invent a consistent editorial framing device that belongs to Style Ease (for example, a numbered collection/edition system and striking crop typography). Make the site feel branded, not like a generic black shopping template. However, never make customers decode where “Products” or “Cart” are.

# 4. THE SIGNATURE FEATURE — STYLE STUDIO / OUTFIT ARCHITECT

This is the marquee differentiator **after core shopping parity and visual coherence have passed**. Build a product people remember, not a widget added for an impressive README checkbox.

**Concept:** **STYLE STUDIO — Compose the Look.** A creative, sophisticated, keyboard-accessible outfit builder based on real catalogue product relationships. It bridges the fashion editorial identity and technical full-stack complexity.

**Experience specification:**

- A beautiful studio workspace with one composition/canvas area and one searchable shop-the-look catalogue panel. Visitors pick a jacket/top, trousers, footwear, accessories, etc. Show selections as accurate photographs/cards, not misleading AI-assembled garments on a fabricated person. Arrange as a designed editorial outfit board with distinctive typography and product metadata.
- Select multiple items with size/colour options; reflect compatible choices. Display exact per-item and total demo prices from authoritative backend data. Show missing categories as suggestions, not errors. Clearly distinguish in-stock/unavailable items.
- Allow add/remove/reorder with pointer controls **and** complete keyboard alternatives. Drag-and-drop may be an enhancement only; a drag-only editor fails accessibility.
- Persist a guest's saved looks in PostgreSQL with stable identifiers, finite limits and ownership; load/save/duplicate/rename/remove, where complete. Avoid exposing another guest's private saved look via guessed IDs.
- Generate shareable look URLs only for explicitly published/public looks with proper authorization and opaque public identifiers. For guest-authored unpublished looks, keep the URL private to the session. Public editorial looks can be curated and seeded with validated product relationships.
- Offer an **Add Outfit to Bag** action that selects valid variants and applies stock limits transactionally, returning accurate successes/partial failures. No client-side arithmetic as the source of truth.
- Show a beautiful editorial preview and optional print/export image only if actually generated from legitimate product photos, with correct attribution and no false claim that items were physically photographed together.
- Add tests for selection, persistence, ownership, invalid variants, deleted/unavailable products, quantity caps, accessibility, back/forward navigation, saved-look reload and mobile layout.

**Implementation rule:** The minimum shippable version is **curated lookbook + shoppable outfit board + server-persisted selections + keyboard controls**. Advanced editor/export/sharing can follow after all core pages are stable. This must not displace parity/security work. If only part of this can be implemented, expose only finished capabilities and document the deferred remainder rather than leaving dead visible buttons.

**Secondary signature opportunities, ordered:**

1. **Collection Stories:** multiple curated editorial chapters with deliberate typographic treatment, curated images, short original copy and actual links to products. Use real collection tables, not a hardcoded fiction disconnected from inventory.
2. **Style Discovery:** small, explainable, deterministic style-preference quiz using genuine catalogue tags/materials/silhouettes. Show *why* suggestions are relevant. No pretend AI intelligence, undisclosed tracking or impossible universal sizing.
3. **Product comparison intelligence:** explain notable material/shape/fit differences using data-driven rules, not generated claims. A structured attribute comparison is sufficient if descriptions aren't rich enough.
4. **Recently viewed / complementary outfit suggestions:** preserve a transparent matching algorithm and test the results, without claiming actual purchase-behavior analytics.
5. **Wishlisted capsule collections:** let guest users save editorial groupings if storage/ownership is correct and the existing wishlist stays understandable.

**Explicitly deferred unless there is a strong, fully secured reason to proceed:** real payment gateway; real shipping-provider API; consumer login/password reset/email verification; multi-role admin CMS; uploads of arbitrary content; user-to-user messaging; generative virtual try-on; face/body image processing; personalized tracking; real customer reviews; real-time inventory from an imaginary warehouse. Use `templ` to generate typed server-rendered HTML/components. **Architectural constraints:**

- HTTP handlers accept/validate/authorize requests, call domain services, and render complete pages or fragments. Do not bury inventory or price logic in templates or handlers.
- Services encode checkout, cart, inventory, saved look and recommendation rules. Repositories parameterize database reads/writes. Templates are nearly logic-free, reusable and accept typed view models.
- All crucial operations are tested at the service and HTTP levels, with integration tests against a real PostgreSQL instance. Do not claim that SQLite is equivalent for PostgreSQL locking, transactions or indexes.
- Consistent explicit errors: validation, not found, forbidden, conflict, temporarily unavailable, unexpected failure. Good messages, correct status codes, request correlation where useful; avoid exposing stack traces, SQL or secret values to users.
- Config uses environment variables with validation and safe local defaults, avoiding inadvertent production insecure settings. Establish environment-specific secure cookie settings. Never check real credentials into git.
- Graceful shutdown and signal handling; deterministic timeouts; bounded DB pools, HTTP request body sizes and form fields; safe `http.Server` timeouts; JSON not required for the primary shopping flow.
- Use structured, privacy-conscious logging, with request IDs and error categories; redact cookies, tokens, queries containing personal data and address contents.
- Optionally include a small `internal/clock` or deterministic service seam for testing timestamp-sensitive logic, rather than flaky tests that assume wall-clock times.

## PostgreSQL schema contract

Design migrations with **foreign keys, uniqueness, checks, meaningful indexes, transactional semantics and deterministic sample data**. Prefer UUID or random opaque public IDs for guest/session-facing resources; preserve numeric legacy product IDs in mapping so old product links can be redirected deterministically.

**Core entity set:**

- `categories(id, slug, name, display_order, ...)`
- `collections(id, slug, title, summary, hero_media_id, published, ...)`
- `products(id, slug, sku, category_id, name, description, material, care, price_minor, currency, status, release_date, ...)`
- `product_variants(id, product_id, sku, size, color, available_demo_qty, sort_order, active, ...)`, with uniqueness per product/size/colour SKU where relevant.
- `product_media(id, product_id, optional_variant_id, path, alt, width, height, sort_order, license/source metadata, ...)`
- `collection_products(collection_id, product_id, position)`
- `guest_sessions(id/hashed_token_key, created_at, last_seen_at, expires_at, ...)`
- `carts(id, guest_session_id, updated_at, ...)`
- `cart_items(cart_id, variant_id, quantity, ...)` with unique `(cart_id, variant_id)`
- `wishlist_items(guest_session_id, variant_id, ...)` with unique ownership keys
- `comparison_items(guest_session_id, product_id, ordinal, ...)` with bounded membership
- `recently_viewed(guest_session_id, product_id, last_viewed_at, ...)`
- `demo_orders(id, guest_session_id, public_code, status, subtotal_minor, total_minor, currency, created_at, idempotency_key, ...)`
- `demo_order_items(order_id, product_id, variant_id, snapshot_title, snapshot_sku, snapshot_size, snapshot_color, snapshot_unit_price_minor, quantity, ...)`
- `editorial_stories`, `editorial_story_products`, and `saved_looks` / `saved_look_items` only as part of a finished editorial/studio feature.

**Database design guidance:** Use appropriate PostgreSQL data types, UTC timestamps, constraints for nonnegative price and sensible quantity limits, stable slugs, explicit indexes on lookup/search/order columns. Consider text search indexes only when actual measured query workload warrants them. Record the migration strategy for unverified old product images and unverified review data. Do not invent product options when porting 20 products. Use preexisting data to seed and curate, with reproducible seed scripts that are idempotent or reset-safe in development and **never destroy production data by default**.

**Money:** Store in integer minor currency units and explicit ISO currency. Choose and document the display currency (existing site uses `$` ambiguously); don't silently turn USD amounts into AUD without a real conversion. At order creation, store immutable line-item snapshots and server-calculated totals so future product changes do not rewrite receipts.

**Variant semantics:** The original application caps quantities by product stock shared across variants. Make this exact choice explicit: either faithfully emulate original demo-stock rules or move to real per-variant demo stock *with documented UX change and tests*. Never promise physical stock reservation. Concurrency-safe DB mutations are required even if the public store is a demo.

**Session design:** Guest sessions should work without creating login accounts. Issue opaque cryptographically random session tokens; store only safe digests server-side if possible. `HttpOnly`, `SameSite` and `Secure` on HTTPS, appropriate expiry/rotation, CSRF tokens bound to sessions or another robust standard pattern, safe cross-tab behavior, no plain session identifiers in URLs, and a plan for periodic expired-data cleanup. Be explicit that guest data persists according to cookie/session lifetime, not indefinitely across devices.

**Transactional correctness to verify:**

1. Two concurrent adds cannot bypass per-product or per-variant capacity rules in the chosen demo model. Use an appropriate transaction/locking strategy and test with concurrent requests.
2. Product options are revalidated against active variants on each write.
3. Guest sessions cannot read another guest's saved items, carts, looks or receipts; missing/forged session cookies don't inherit protected data.
4. Checkout retries with the same idempotency key cannot create duplicate orders or over-consume demo stock.
5. Transaction failure rolls back both order and cart operations coherently.
6. Updates to a product's price do not mutate existing immutable receipt snapshots.
7. Deleted/deactivated variants and malformed cart payloads are safely handled, with transparent user feedback.
8. Out-of-stock or unsupported variants cannot be purchased merely by forging a POST request.
9. A DB outage produces safe error UX, not silently fake successful persistence.
10. The seed process cannot be invoked accidentally against a production DB through routine application startup.

# 6. SECURITY, PRIVACY & OPERATIONS: HIGH BAR WITHOUT THEATER

Before any persistent guest data is exposed publicly:

- **OWASP-aligned input/output handling:** `templ` escaping by default; avoid raw HTML and unvalidated dynamic URLs; use templ's sanctioned safe URL approach with explicit validation. SQL parameters only. Reasonable request limits, string length bounds, strict sort/filter allowlists, safe error messages, no directory traversal from asset handling, safe content types.
- **CSRF for all mutations**, including HTMX, ordinary HTML forms, checkout, saved looks and review submissions. Session-bound token/standard middleware + origin/referer checks where appropriate, not just a custom header. Ensure `SameSite` alone isn't the only barrier. Test missing/invalid tokens and cross-site requests.
- **Safe session cookies:** secure HTTPS flags in production, HttpOnly, correct SameSite/domain/path/expiry, safe rotation/expiry handling. No session token/secret in logs. Harden against session fixation and replay within realistic scope.
- **Authorization:** Guest-owned data must only be available to its owner. A demo order public code is not authorization by itself unless explicitly structured as a revocable, high-entropy secret capability URL with privacy risk evaluated; default to session ownership. No unguarded admin route.
- **Authentication later:** If administrative publishing/auth is implemented after the core, use proven auth libraries/patterns, secure password hashing or external trusted identity and explicit roles. Do not make a “temporary” admin password or client-side gate live.
- **Content Security Policy:** Implement a practical CSP that is compatible with the specific pinned HTMX 4 code and any trusted event wiring. Prefer external local scripts/styles with appropriate nonces/hashes if needed; avoid broad `unsafe-inline` and `unsafe-eval` as a convenience. Validate actual functionality under the policy.
- **Other headers:** Sensible `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`, frame protection via CSP, correct cache control for guest-sensitive content, and HTTPS/HSTS only when appropriate to the deployment environment.
- **Abuse resistance:** Rate-limit mutation-heavy endpoints and especially reviews/auth attempts if those exist. Handle header/IP trust correctly behind a proxy; never trust arbitrary `X-Forwarded-For` from the open internet.
- **Privacy minimization:** Collect no real payment data and minimize demo customer personal details. Clear, real retention policy for guest records; do not publish sensitive details in logs, link preview, telemetry, screenshots, test artifacts or receipts available to strangers. Consent dialogs only where warranted by actual tracking requirements; no fake cookie banners.
- **Database resilience:** Connection timeout, pool limits, readiness distinct from liveness, transactions, bounded pagination, indexes and explainable failure UX; prepared migrations and rollback strategy. Backups need actual configured provider mechanisms, not a `BACKUPS_ENABLED=true` fiction.
- **Deployment hygiene:** `.env.example` only contains placeholders; `.env` gitignored; production credentials stored in host secrets; non-root runtime user; small container image; pinned dependencies; reproducible `go.sum`; no private tokens exposed in Docker build args/layers. `govulncheck` or comparable Go advisories, secret scanning, Docker security checks when available. Report warnings rather than disabling them.
- **Accessibility is also safety:** Proper live announcements for order confirmation, error focus, mobile dialogs, dangerous remove actions, loading feedback and complete keyboard path. Never hide essential controls behind mouse-hover animations.

Generate `docs/THREAT_MODEL.md` using a concise assets/entry-points/attacker-goals/mitigations table plus abuse-case tests. Do not claim certification or regulatory compliance simply because checks pass.
